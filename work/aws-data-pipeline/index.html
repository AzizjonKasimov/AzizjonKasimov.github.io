Serverless data pipeline on AWS

Pricing research needed a steady feed of used-parts market data. I designed, built, and ran an event-driven pipeline on AWS that reached about 5 million listings a day in testing.

My role
Sole designer, builder, and operator, as part of taking over AWS from a senior engineer who left.
Result
~5M listings per day in testing. Ran daily in production with monitoring and alerts.
Stack
AWS Lambda (Docker images), SQS, EventBridge, RDS PostgreSQL, RDS Proxy, CloudWatch, SNS, ECR, Python
Scope
Marketplace listings for the 7 vehicle brands the company handles, collected every day

The problem

The company's price-prediction work needed broad, fresh market data. The target was about 5 million listings a day across the 7 vehicle brands it handles.

The pipeline had to be reliable, stay within budget, and cope with a source that limits how fast it can be read.

Architecture

Built to slow down, not fall over

A data source that limits request rates will push back. The pipeline was designed for that:

  • Circuit breaker. When pages start getting blocked, workers pause instead of retrying harder. A shared cooldown state lives in PostgreSQL.
  • Adaptive rate limiting. Request timing has jitter, the pipeline backs off automatically when the source pushes back, and workers ramp up gradually after a cooldown.
  • Safe concurrency. Workers claim targets safely, retry, and recover stuck jobs, so many of them can run in parallel without clashing.

Observability and operations

  • Alarms for the things that matter: orchestrator down, worker failures, concurrency throttling, queue backlog and message age, blocked-page rate, database write failures, and listings per day.
  • Health checks with AWS CLI scripts, plus a small read-only Lambda that posts database health to CloudWatch.
  • Written procedures for throttling or stopping Lambdas and purging queues, so a runaway job can't run up costs.

Hardening after senior review

PostgreSQL statement timeouts, a URL allow-list, response-size limits, failing fast on suspicious empty pages, atomic write paths, and structured failure capture. I also removed an expensive COUNT(*) from the hot path, added index maintenance tools, and set retention policies for ECR images and CloudWatch logs to control cost.

Results

  • ~5M/daylistings, reaching the target in testing
  • Dailycollection, storage, and alerting in production
  • 7 brandscovered for the company's pricing research

What I learned: when the source tightened its rate limits, sustainable throughput fell to about 5,000 listings a day, which became the normal operating rate. At this scale, the real limit is often the data source, not the infrastructure, so back-off has to be part of the design from day one.
