Production G-Man Auto Parts · 2025–2026

AI semantic search for auto parts

Buyers and suppliers needed to find the exact part for a specific car by typing plain words, in more than one language. I built the search end to end, plus a test suite that proved it met the 95% accuracy bar.

My role
Only AI/ML engineer. I owned the design, embeddings, entity recognition, LLM steps, evaluation, and production.
Result
95%+ accuracy on the required 3,000-part test. The R&D project was approved.
Stack
Python, Django REST Framework, Weaviate, spaCy, OpenAI API (GPT-4o-mini), Celery, PostgreSQL, AWS S3, React
Scale
A catalog of 2M+ parts records and 300K+ searchable listings (Kia, Hyundai, SsangYong, Chevrolet)

The problem

People describe the same part in many ways: “headlight” or “head lamp”, informal names, or other languages. But the right answer is one part number for one exact car: brand, model, year, fuel, transmission, generation, and side (left or right, front or rear).

Rigid keyword filters could not handle this. The company needed natural-language search that returns the correct part with high precision. It also had to pass a formal accuracy test for an R&D project.

How a query flows

What I built

  • Vector search core. I embedded the parts catalog in Weaviate and built the search service in Django REST Framework. I designed the text that gets embedded (field labels, part side, car year, and curated synonyms) to raise recall.
  • Entities as hard filters. spaCy pulls structured facts out of a free-text query and turns them into exact filters. The vector search handles wording; the filters make sure the car and the side are right.
  • Two search modes. Product search for buyers. Auto-matching for suppliers: an uploaded part is matched to catalog records, and each distinct part number becomes its own result.
  • Multilingual queries. Non-English queries go through an LLM step. Moving from GPT-3.5-Turbo to GPT-4o-mini gave better quality at a lower cost, and the language check keeps LLM calls to a minimum.
  • Relevance tuning. An LLM re-ranker removes clearly wrong results. A part-name alias system (for example, “headlight” → “Head Lamp Assembly”) raised accuracy on everyday wording.
  • Frontend wiring. I connected the React/TypeScript store and admin tools to the search APIs: filters feed the query, matches autofill forms, and results sort by relevance with a certainty threshold.

Measuring accuracy

Accuracy had to be measured, not guessed. I built an internal testing page that runs the same pipeline as production search on a fixed, curated test set.

  • Metrics: accuracy@1 and accuracy@3, precision, recall, F1, a confusion matrix, and cross-validation.
  • Repeatable runs: automated or manual. Each run records who ran it and whether LLM preprocessing was on.
  • Safe by design: test data lives in separate collections, with guards so a test can never touch production data.
  • Error analysis: I traced “no results” cases to stale test objects, SKU-to-catalog mismatches, clashing entity patterns, and body-color handling, then fixed each one.

Results

  • 95%+accuracy on the required 3,000-part evaluation set
  • ApprovedR&D project, after passing the accuracy bar
  • 300K+searchable listings, on a catalog of 2M+ parts records

The search went live in production for both buyers and suppliers. I also ran the automated accuracy tests in production and fixed the issues they found.
