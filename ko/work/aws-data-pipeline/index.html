AWS 서버리스 데이터 파이프라인

가격 분석에는 중고 부품 시장 데이터가 꾸준히 필요했습니다. 저는 AWS에서 이벤트 기반 파이프라인을 설계하고 구축해 운영했으며, 테스트에서 하루 약 500만 건의 매물을 수집했습니다.

역할
퇴사한 시니어 엔지니어에게서 AWS를 인수받으며, 설계와 구축, 운영을 혼자 맡았습니다.
결과
테스트에서 하루 약 500만 건. 프로덕션에서 모니터링과 알림을 갖추고 매일 운영했습니다.
기술 스택
AWS Lambda (Docker 이미지), SQS, EventBridge, RDS PostgreSQL, RDS Proxy, CloudWatch, SNS, ECR, Python
범위
회사가 취급하는 7개 차량 브랜드의 마켓플레이스 매물을 매일 수집

문제

회사의 가격 예측 작업에는 폭넓고 최신인 시장 데이터가 필요했습니다. 목표는 회사가 취급하는 7개 차량 브랜드 전체에서 하루 약 500만 건의 매물이었습니다.

파이프라인은 안정적이어야 했고, 예산 안에서 운영되어야 했으며, 읽기 속도를 제한하는 데이터 소스에도 대응해야 했습니다.

아키텍처

무너지지 않고 속도를 늦추는 설계

요청 속도를 제한하는 데이터 소스는 결국 제동을 겁니다. 파이프라인은 이를 전제로 설계했습니다.

  • 서킷 브레이커. 페이지가 차단되기 시작하면 워커는 더 세게 재시도하는 대신 잠시 멈춥니다. 공유 쿨다운 상태는 PostgreSQL에 저장됩니다.
  • 적응형 속도 제한. 요청 간격에 지터를 두고, 소스가 제동을 걸면 자동으로 속도를 줄이며, 쿨다운 후에는 워커를 점진적으로 늘립니다.
  • 안전한 동시성. 워커는 대상을 안전하게 선점하고, 재시도하며, 멈춘 작업을 복구합니다. 그래서 많은 워커가 충돌 없이 병렬로 실행됩니다.

관측성과 운영

  • 중요한 항목에 대한 알람: 오케스트레이터 중단, 워커 실패, 동시성 스로틀링, 큐 적체와 메시지 대기 시간, 차단된 페이지 비율, 데이터베이스 쓰기 실패, 일일 매물 수.
  • AWS CLI 스크립트를 이용한 상태 점검, 그리고 데이터베이스 상태를 CloudWatch에 보내는 작은 읽기 전용 Lambda.
  • Lambda를 제한하거나 중지하고 큐를 비우는 문서화된 절차. 폭주하는 작업이 비용을 키우지 못하게 합니다.

시니어 리뷰 후 안정성 강화

PostgreSQL 구문 타임아웃, URL 허용 목록, 응답 크기 제한, 의심스러운 빈 페이지에서의 빠른 실패 처리, 원자적 쓰기 경로, 구조화된 실패 기록을 적용했습니다. 또한 자주 실행되는 경로에서 비용이 큰 COUNT(*)를 제거하고, 인덱스 유지 관리 도구를 추가했으며, 비용 관리를 위해 ECR 이미지와 CloudWatch 로그의 보존 정책을 설정했습니다.

결과

  • 약 500만/일매물 수, 테스트에서 목표 달성
  • 매일프로덕션에서의 수집, 저장, 알림
  • 7개 브랜드회사의 가격 분석을 위한 수집 범위

배운 점: 소스가 속도 제한을 강화하자 지속 가능한 처리량은 하루 약 5,000건으로 떨어졌고, 이것이 평소 운영 수준이 되었습니다. 이 규모에서는 인프라보다 데이터 소스가 실제 한계인 경우가 많으므로, 백오프는 처음부터 설계에 포함해야 합니다.

이 글은 단순화한 내용입니다. 회사 코드, 내부 데이터, 비공개 URL은 포함하지 않았으며, 데이터 소스의 이름도 밝히지 않았습니다.
