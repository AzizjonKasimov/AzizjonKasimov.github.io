基于 AWS 的无服务器数据管道

定价研究需要稳定的二手零件市场数据来源。我在 AWS 上设计、构建并运维了一个事件驱动的数据管道，测试中达到每天约 500 万条商品信息。

我的角色
唯一的设计者、开发者和运维者，这是我在一位资深工程师离职后接手 AWS 工作的一部分。
成果
测试中每天约 500 万条商品信息。在生产环境中每日运行，配有监控和告警。
技术栈
AWS Lambda（Docker 镜像）、SQS、EventBridge、RDS PostgreSQL、RDS Proxy、CloudWatch、SNS、ECR、Python
范围
公司经营的 7 个汽车品牌在交易平台上的商品信息，每天采集

问题

公司的价格预测工作需要广泛且新鲜的市场数据。目标是针对公司经营的 7 个汽车品牌，每天采集约 500 万条商品信息。

这个数据管道必须稳定可靠、控制在预算之内，并能应对一个限制读取速度的数据源。

架构

宁可减速，也不宕机

限制请求频率的数据源会进行反制。这个管道就是为此而设计的：

  • 熔断机制。当页面开始被拦截时，工作函数会暂停，而不是更猛烈地重试。共享的冷却状态保存在 PostgreSQL 中。
  • 自适应限流。请求时间带有随机抖动；当数据源开始反制时，管道会自动退避；冷却结束后，工作函数会逐步恢复负载。
  • 安全并发。工作函数能安全地认领目标、重试并恢复卡住的任务，因此许多工作函数可以并行运行而互不冲突。

可观测性与运维

  • 告警覆盖真正重要的情况：编排器宕机、工作函数失败、并发限流、队列积压和消息滞留时长、页面被拦截的比例、数据库写入失败，以及每天的商品信息数量。
  • 健康检查使用 AWS CLI 脚本，另有一个小型只读 Lambda 函数把数据库健康状况上报到 CloudWatch。
  • 书面操作规程说明如何限制或停止 Lambda 函数、如何清空队列，防止失控的任务推高成本。

资深评审后的加固

PostgreSQL 语句超时、URL 白名单、响应大小限制、遇到可疑的空页面时快速失败、原子写入路径，以及结构化的失败记录。我还把开销很大的 COUNT(*) 从热点路径中移除，添加了索引维护工具，并为 ECR 镜像和 CloudWatch 日志设置了保留策略，以控制成本。

结果

  • ~500 万/天商品信息，测试中达到目标
  • 每日在生产环境中采集、存储和告警
  • 7 个品牌覆盖公司的价格研究

经验总结：当数据源收紧频率限制后，可持续的吞吐量降到每天约 5000 条商品信息，并成为常态运行速率。在这种规模下，真正的瓶颈往往是数据源，而不是基础设施，因此退避机制必须从第一天起就纳入设计。
