用于目录数据的 LangGraph 智能体

导入第三方目录数据曾是数据团队缓慢的手工工作。我构建了一个智能体工作流，把简短的请求转换成干净、可直接入库的零件数据，支持定时调度、可断点续跑的任务，以及任何人都能核查的报告。

我的角色
唯一的开发者：负责调研、架构、智能体、定时调度和演示界面。
状态
为数据团队打造的可运行原型，带有演示界面。我于 2026 年 7 月离职时，它尚未投入生产。
技术栈
Python、LangGraph、OpenAI API、APScheduler、PostgreSQL
范围
针对公司经营的 7 个汽车品牌，按品牌、车型、年份和地区发出的请求

问题

把第三方车辆和零件数据导入公司目录是重复的手工工作。需要有人选择许多参数、下载数据、清洗数据，并把每条记录映射到正确的目录表中。

目标是把这项工作自动化，让数据团队不必再手动处理。

工作原理

我构建了什么

  • 先求简单，再求可预测。第一个版本接收自然语言请求，带有澄清步骤，并记录智能体的每一步以便调试。工作流稳定后，我把自由文本换成了下拉选项，让每次运行都可以重复。
  • 为什么用 LangGraph。LLM 只承担一小部分工作，但 LangGraph 依然物有所值：工作流结构清晰、易于检查，并能在失败后续跑。
  • 为超大任务而设计。分块、可续跑的保存方式能处理拥有超过 10 万个变体的车型。
  • 定时调度。APScheduler 配有用于定时和手动运行的小型界面，我还修复了任务重复注册的问题。
  • 可审核的输出。自动生成的报告展示每个批次是如何规范化和映射的，非工程人员也能审核结果。
  • 文档。目录结构的参考文档：智能体读取哪些表、写入哪些表。

工程判断

在动手之前，我比较了自建与采购两种方案。我研究了现有的 AI 数据采集工具和工作流引擎（Airflow、Prefect、Celery），选择了一种符合项目阶段的轻量方案，并保留了日后扩展的路径。

我还让任务范围和计费 API 的用量保持可见，而不是把它们隐藏在自主行为背后。这种设计减少了手工工作，同时让人始终掌控成本和数据。

状态

一个带定时调度和演示界面的可运行原型，供数据团队使用。当时它正在被整合进一个统一的内部管理工具。我于 2026 年 7 月离职时，它尚未投入生产。
