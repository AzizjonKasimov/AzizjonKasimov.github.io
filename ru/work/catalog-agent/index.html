Прототип G-Man Auto Parts · 2026

LangGraph-агент для данных каталога

Загрузка данных стороннего каталога была для дата-команды медленной ручной работой. Я создал агентный процесс, который превращает короткий запрос в чистые данные о запчастях, готовые для каталога, — с запуском по расписанию, возобновляемыми задачами и отчётом, который может проверить любой.

Моя роль
Единственный разработчик: исследование, архитектура, агент, планировщик и демо-интерфейс.
Статус

Стек
Python, LangGraph, OpenAI API, APScheduler, PostgreSQL
Охват
Запросы по марке, модели, году и региону для 7 марок автомобилей, с которыми работает компания

Задача

Загрузка сторонних данных об автомобилях и запчастях в каталог компании была однообразной ручной работой. Нужно было выбрать множество параметров, скачать данные, очистить их и сопоставить каждую запись с нужными таблицами каталога.

Цель — автоматизировать эту работу, чтобы дата-команде больше не приходилось делать её вручную.

Как это работает

Что я сделал

  • Сначала просто, затем предсказуемо. Первая версия принимала запрос на естественном языке, включала этап уточнения и трассировала каждый шаг агента для отладки. Когда процесс стал стабильным, я заменил свободный текст выпадающими списками, чтобы запуски были воспроизводимыми.
  • Почему LangGraph. LLM выполняет лишь небольшую часть работы. Но LangGraph всё равно оправдывает себя: процесс структурирован, его легко проверять, и он умеет продолжать работу после сбоя.
  • Рассчитан на очень большие задачи. Сохранение по частям с возможностью возобновления справляется с моделями автомобилей, у которых более 100 тыс. вариантов.
  • Планирование. APScheduler с простым интерфейсом для запусков по расписанию и вручную, включая исправление повторной регистрации задач.
  • Результат, который можно проверить. Автоматические отчёты показывают, как каждый пакет был нормализован и сопоставлен, поэтому результат могут проверить и люди без инженерного опыта.
  • Документация. Справочник по схеме каталога: какие таблицы агент читает, а в какие пишет.

Инженерные решения

Прежде чем начать, я сравнил два пути: сделать самим или купить готовое. Я изучил существующие ИИ-инструменты для сбора данных и движки рабочих процессов (Airflow, Prefect, Celery) и выбрал лёгкое решение, которое подходило проекту на его стадии и оставляло возможность масштабироваться позже.

Кроме того, я сделал объём задач и платное использование API видимыми, а не спрятал их за автономным поведением агента. Такое решение сокращает ручную работу, но оставляет контроль над расходами и данными за людьми.

Статус

Рабочий прототип с планировщиком и демо-интерфейсом для дата-команды. Его встраивали в единую внутреннюю админ-панель. Когда я ушёл из компании в июле 2026 года, он ещё не был в продакшене.
